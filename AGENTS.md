# Shikiri-yaku — Agent Conventions

- **Read first**: `docs/design.md` (purpose, architecture, engineering constraints). When this file and the design differ, the design wins; report the difference instead of choosing silently. Do not edit `docs/design.md`; if it is wrong or silent, say so in the report.
- **Conventions**: SOLID, KISS, YAGNI. Dependencies point inward and everything a class needs comes through its constructor; import-linter enforces the layers, so never weaken a contract. Every number is a setting in `settings.py`; limits that belong to others are named constants. Names come from the design's vocabulary. Comments explain why, never what. Docstrings only on public contracts. No code for a case the design does not describe.
- **Safety**: a model never writes a command; code builds every host command from the fixed recipes. Nothing runs on the host without the PO's approval. Tests never install packages, run `sudo`, change the host, use the network, or read, log or commit the token file and secrets; they use fakes and harmless commands through `CommandRunner`.
- **Parsing**: validated data is parsed by pydantic models. Our own files use `extra="forbid"`; payloads of other systems (Shikiru, Telegram) use `extra="ignore"` and declare only the fields we read. Values the other side may extend are `str` with named constants, never a closed enum.
- **Tests**: protect a stated behavior, such as the guarantees under Verification in `docs/design.md`. Table-driven where the rule is a table; fakes for ports; real SQLite in memory. No tests of message wording, getters, config defaults or mocks of internal classes; do not chase coverage.
- **Verification**: for documentation-only changes review the diff and run `git diff --check`. For code, `uv run poe check` (use `uv run poe fix` to format) must pass before the final commit and the report. If the gate or a pinned dependency fails for a reason unrelated to your change, say so with the evidence.
- **Tasks**: `tasks/plan.md` holds the task and its acceptance criteria; `tasks/todo.md` the checklist: tick only your own line. One task, one change.
- **Commits**: Conventional commits, one coherent change each. The subject is what the release notes show, so write it for a user: `type(scope): what changed`. A change that breaks behavior, configuration, the journal schema or the minimum Shikiru version marks the type with `!` or adds a `BREAKING CHANGE:` line to the body.
- **Boundaries**: never push, never touch another branch's work, never edit files outside this repository.
